# Antigravity Instructions: Security & Design Hardening
**Project:** Homeopathy-Clinic-System (Laravel + Inertia/React + MySQL, target: shared cPanel hosting)
**Review basis:** `Homeopathy-Clinic-System.zip` (source code + `.env` + SQL dumps), read statically.

## 0. What this review covered, and its limits

**Reviewed:** routes, controllers, middleware, models, migrations, seeder, Blade views, the React layout, config files, the `.env`, the SQL dumps in `database/`, the logs, and the leftover files in the project root.

**Not done (be aware):**
- Nothing was executed. The review environment has no PHP runtime, so there was no live scan, no running app, and no screenshots. Every finding comes from reading code and data.
- `composer audit` / `npm audit` were not run (no Packagist access). The agent must run them in Phase 6.
- The SQL dumps contain **no patient, visit or prescription rows yet**, so no real patient data was exposed in this zip. The risks below are about what happens once you go live.

**Already fixed since the last review (verified in code, do not redo):** per-action route permissions for patients, medicines, symptoms, visits, symptom-medicine map and appointments; the Super Admin role can no longer be edited; last-Super-Admin guards on user update/delete; the `is_active` check at login; login rate limiting (5 attempts); soft deletes on patients, visits and prescription items; public pages now read Settings and use compiled Tailwind (the CDN is gone); permission-filtered desktop and mobile nav; delete confirmations; dompdf has `enable_php=false`, `enable_remote=false` and a `chroot`; doctor photo uploads are limited to jpg/png/webp, 2 MB.

## 2. Standing rules (append to AGENTS.md or add as an "Always On" rule)

```
## Security & design hardening rules
- This is a clinical records system. Treat all patient data as sensitive. Never log, echo, or
  commit patient data, passwords, tokens, or .env values. Never print secrets in chat or artifacts.
- Authorization is enforced SERVER-SIDE (route middleware or policies). Hiding a button is never enough.
  Every state-changing route needs its own permission check matching the action
  (view / create / update / delete). Never gate a write route with a *.view permission.
- Only the "Super Admin" role may manage users, roles, permissions, clinic settings, and audit logs.
- Never edit the "Super Admin" role's permissions. Never allow removal, deactivation, or deletion of the last Super Admin by any path.
- Validate every request field with a Form Request class: type, length, enum, exists:, array item rules.
- Do not add external CDNs or hotlinked assets. Self-host fonts and images (the host is shared cPanel, and privacy matters).
- Production target is shared cPanel PHP hosting. No persistent Node process. Assets are built locally with `npm run build`.
- Add or update automated tests for every fix. Run `php artisan test`, `vendor/bin/pint --test`, and `npm run build` before declaring a phase done.
- Do not remove existing behavior that is not in scope. Prefer small, reviewable diffs. Ask before destructive migrations.
```

## 4. Findings summary (severity-ranked)

| ID | Severity | Finding |
|---|---|---|
| S1 | **High** | Seeded default passwords are live in the database dump for all 3 accounts, and `must_change_password` is `0` for all of them, so the force-change step was bypassed. Plaintext defaults sit in `DatabaseSeeder.php`. |
| S2 | **High** | Privilege escalation: the whole `users` and `roles` resources are gated by `*.view` only. Anyone granted `users.view` can create a Super Admin, assign Super Admin to themselves, or reset the Super Admin's password. |
| S3 | **High** | The `settings.view` group also protects every write: clinic settings update, and full create/update/delete of doctors, advice items and food restrictions. Same bug class as before, still present here. |
| S4 | **High** | `DELETE /profile` lets any staff member delete their own account with no last-Super-Admin guard. Deleting the only Super Admin locks everyone out. |
| S5 | **High** | The zip shipped real secrets and live artifacts: `.env` (DB `root` user and password, `APP_KEY`, `APP_DEBUG=true`), an active admin session row, logs with local paths and stack traces, and a sample prescription with a patient name. Treat all of it as exposed. |
| S6 | Medium | The audit log is readable by anyone with `reports.view` (Doctor, Accountant) and `logUnguarded()` stores full before/after patient data in it. |
| S7 | Medium | Finalized visits can be edited or deleted like drafts; prescription items are silently deleted and recreated on every edit. |
| S8 | Medium | Input validation gaps: `prescription_items`, `symptoms`, `advice_items`, `food_restrictions` are only validated as `array`; user creation allows 8-character passwords; report date filters are unvalidated; public form `message` has no length limit. |
| S9 | Medium | Public `POST /appointment-requests` has no throttle, honeypot or CAPTCHA, so it can flood the database. |
| S10 | Medium | Production hardening missing: `APP_DEBUG=true`, `APP_ENV=local`, `SESSION_SECURE_COOKIE` unset, `SESSION_ENCRYPT=false`, no security headers, app uses the MySQL `root` account. |
| S11 | Medium | Over-exposure of patient data: the visit create/edit pages ship **every** patient to the browser (`Patient::all()`); the Reports page loads all visits in range with no pagination. |
| S12 | Low-Med | Ziggy `@routes` in the root template publishes every route name (including admin routes) to unauthenticated visitors on the login page. |
| S13 | Low-Med | Dev tooling in the project: `laravel/boost` (MCP server, browser-log capture), `.mcp.json`, `boost.json`, `.phpunit.result.cache`, `Prescription.jpeg`, `database/*.sql`. None may reach production. |
| S14 | Low | URL fields use the loose `url` rule (accepts `ftp://`, `file://`, `data://`; `javascript:` is rejected); the developer link uses `target="_blank"` with no `rel`; pagination uses `dangerouslySetInnerHTML` (labels come from Laravel, but still avoidable). |
| S15 | Low | Dead data: `prescription_header_image` is validated and stored but never used (arbitrary string, a future SSRF/local-file risk if ever fed to dompdf). `clinic_settings` still has the hero/social columns that moved to `doctors`. |
| S16 | Low | Test coverage is only the default Breeze auth tests. There are no authorization tests, which is how S2/S3 got through. |

## 5. Phased instructions

### Phase 0: Secrets and data hygiene (do this yourself first, then tell the agent)

These are manual because they involve real secrets. The agent must not do them.
- [ ] **Rotate** the MySQL password and `APP_KEY` (treat the current ones as leaked via the zip). Rotating `APP_KEY` invalidates existing sessions, which is fine pre-launch.
- [ ] **Truncate the `sessions` table** (the dump contains a recent admin session).
- [ ] **Change all three seeded account passwords** (admin, doctor, receptionist) to strong unique ones, or delete the doctor and receptionist test users before launch.
- [ ] Create a **dedicated MySQL user** for the app with privileges on the clinic database only (not `root`).
- [ ] Delete from the project (and from anything uploaded to the server): `database/*.sql`, `database/database.sqlite`, `Prescription.jpeg`, `storage/logs/*.log`, `.phpunit.result.cache`.
- [ ] Never upload `.env` inside any zip again. Build the production `.env` directly on the server (template in Phase 5).

### Phase 1: Authentication and privilege escalation (S1, S2, S4)

**Files:** `database/seeders/DatabaseSeeder.php`, `routes/admin.php`, `app/Http/Controllers/Admin/UserController.php`, `RoleController.php`, `app/Http/Controllers/ProfileController.php`, `routes/web.php`.

1. **Seeder (S1):** stop hardcoding passwords. Read the Super Admin password from `env('SEED_ADMIN_PASSWORD')`; if unset, generate a random 20-character one and print it **once** to the console. Create the Doctor and Receptionist test users **only when `app()->environment('local')`**. Keep `must_change_password = true`.
2. **Super-Admin-only modules (S2):** put the `users` and `roles` resource routes behind `role:Super Admin` middleware (the alias already exists), in addition to per-action permissions (`users.create` etc., split exactly like patients). The Users and Roles nav links should only render for Super Admin.
3. **Role assignment guard (S2):** in `UserController@store/update`, validate `roles.*` with `Rule::exists('roles','name')`, and reject the "Super Admin" role unless the acting user is Super Admin. Also require `current_password` re-entry when an admin changes another user's password. Same for `RoleController`: validate `permissions.*` with `Rule::exists('permissions','name')`.
4. **Profile (S4):** remove the `DELETE /profile` route, the controller method and the delete-account section in `Profile/Edit`. Staff are deactivated by a Super Admin, not self-deleted. (If you want to keep it, add the same last-Super-Admin guard used in `UserController@destroy`.)
5. **Password policy:** in `AppServiceProvider::boot()` call `Password::defaults(fn () => Password::min(12)->mixedCase()->numbers()->symbols())` and use `Password::defaults()` in `UserController` instead of `min:8`.

**Tests to add (feature tests):** Receptionist and Doctor get **403** on every `/admin/users*` and `/admin/roles*` route; a non-Super-Admin cannot create a user with the Super Admin role; the last Super Admin cannot be deleted by any route; `DELETE /profile` is gone (404/405).

### Phase 2: Settings, audit log and permission granularity (S3, S6)

1. **Settings group (S3):** split the `settings.view` group in `routes/admin.php` the same way as patients: `GET` routes on `settings.view`, `PUT settings` and doctor/advice/food create/update/delete on `settings.update`/`.create`/`.delete`. Add permissions `doctors.*`, `advice_items.*`, `food_restrictions.*` to the seeder if you want finer control; otherwise use `settings.update` for every write.
2. **Audit log (S6):** create a new permission `activity_logs.view`, give it to Super Admin only, and gate `/admin/activity-logs` on it (not `reports.view`). In `Patient`, `Visit`, `PrescriptionItem` change `logUnguarded()` to `logOnly([...non-sensitive fields...])` plus `logOnlyDirty()` and `dontSubmitEmptyLogs()`. Do not log full `known_allergies` / `diagnosis_notes` / `bp_symptoms_notes` text; log "changed" instead. Add `ClinicSetting` to the logged models.
3. Export of reports (if added later) must use `reports.export`, not `reports.view`.

**Tests:** Receptionist/Doctor get 403 on settings writes and on the log page; Accountant can see reports but not logs.

### Phase 3: Clinical-record integrity and input validation (S7, S8, S11)

1. **Form Requests:** create `StoreVisitRequest` / `UpdateVisitRequest` with full rules: `prescription_items.*.medicine_id => exists:medicines,id`; `timing => required|array|min:1`; `timing.* => in:morning,noon,afternoon,night`; `before_after => in:before,after`; `dose_qty => integer|min:1|max:50`; `dose_unit => in:drops,pills`; `dilution_note => nullable|string|max:255`; `duration_days => nullable|integer|min:1|max:365`; `symptoms.*`, `advice_items.*`, `food_restrictions.* => exists:...`; cap array sizes (e.g. max 10 prescription items). Also validate `age_at_visit` (0-120), `follow_up_date` after-or-equal `visit_date`, and max lengths on the text fields.
2. **Finalized visits (S7):** once `status = finalized`, block `update`/`destroy` unless the user has a new permission `visits.amend`; an amendment creates a logged change with a reason field. Keep prescription items append-only: on edit, soft-delete old rows (the model already has `SoftDeletes`) instead of hard-deleting, and never reuse IDs.
3. **Stop shipping all patients (S11):** replace `Patient::all()` in `VisitController@create/edit` with an async search endpoint (`/admin/patients/search?q=`, throttled, min 2 characters, max 10 results returning only id, number, name, age) and a searchable combobox in the visit form. Paginate or hard-limit the Reports page (default to the last 30 days, `paginate(50)`), and validate `start_date`/`end_date` as dates with `end_date >= start_date`.
4. **Other validation:** patient phone `regex:/^(\+?8801|01)[3-9]\d{8}$/`; appointment `message => max:1000`; all URL fields use `url:http,https`; add `rel="noopener noreferrer"` to every `target="_blank"` link; remove the unused `prescription_header_image` field and write a migration dropping it and the stale hero/social columns from `clinic_settings` (back up first; ask before running).

**Tests:** posting malformed `prescription_items` returns a 422 (never a 500); a finalized visit cannot be edited or deleted without `visits.amend`; the visit form no longer includes a full patient list in the page props.

### Phase 4: Public form abuse and transport/session hardening (S9, S10, S12)

1. **Appointment form (S9):** add `->middleware('throttle:5,1')` to `POST /appointment-requests`, a honeypot field (hidden `website` input that must stay empty) and a minimum-fill-time check (signed timestamp, reject submissions under 3 seconds). Cap total requests per IP per day. Do not add a third-party CAPTCHA unless the doctor wants one (privacy and external dependency).
2. **Security headers middleware (S10):** add `app/Http/Middleware/SecurityHeaders.php` appended to the `web` group:
   `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`, and `Strict-Transport-Security` only when the request is HTTPS. Add a `Content-Security-Policy` that allows `'self'`, and move the inline carousel script in `home.blade.php` into the Vite bundle so no `unsafe-inline` script is needed. Test the CSP in report-only mode first.
3. **Ziggy (S12):** change `@routes` in `app.blade.php` to expose only what guests need (e.g. `@routes(['only' => ['login','password.*','home']])`) or use Ziggy groups so admin route names are only sent to authenticated users.
4. **Force HTTPS and proxy trust:** in production call `URL::forceScheme('https')` and configure trusted proxies if the host sits behind one.

### Phase 5: Production configuration, deployment and dev-tool removal (S10, S13)

- Production `.env` (create on the server, never in the repo): `APP_ENV=production`, `APP_DEBUG=false`, `APP_NAME="<Clinic Name>"`, `APP_URL=https://<domain>`, `LOG_LEVEL=error`, `LOG_STACK=daily`, `SESSION_SECURE_COOKIE=true`, `SESSION_ENCRYPT=true`, `SESSION_SAME_SITE=lax`, `SESSION_LIFETIME=60`, DB credentials for the dedicated limited user, real SMTP settings (the current `MAIL_MAILER=log` means password-reset emails go nowhere; for a staff-only app, either configure SMTP or remove the forgot-password routes and let the Super Admin reset passwords).
- Build with `composer install --no-dev --optimize-autoloader` so `laravel/boost` and other dev packages are not installed. Add a deployment check that `/_boost/*` and the browser-log endpoint return 404 in production.
- Do not upload `.agents/`, `AGENTS.md`, `.mcp.json`, `boost.json`, `tests/`, `database/*.sql`, or `.env.example` secrets. Only the app folder (outside `public_html`) plus `public/` contents belong on the server.
- `public/.htaccess` additions: deny dotfiles (`<FilesMatch "^\.">` -> deny), keep `Options -Indexes`. Add an `.htaccess` inside `public/storage/` that disables script execution (`php_flag engine off` / `RemoveHandler .php`) so an uploaded file can never run as PHP.
- Uploads: keep the current mime allowlist; additionally re-encode uploaded images (e.g. with GD) to strip metadata, and never trust the original filename (the code already uses `store()` hashed names, keep it).
- Add `.gitignore` entries: `database/*.sql`, `database/*.sqlite`, `Prescription.jpeg`, `.phpunit.result.cache`, `storage/logs/*`.
- Document a cPanel cron for nightly MySQL backups (encrypted, off-server). Patient data needs a tested restore procedure.
- Optional defense in depth: Laravel `encrypted` casts on free-text clinical notes (`diagnosis_notes`, `bp_symptoms_notes`, `known_allergies`). Note this breaks SQL `LIKE` search on those fields, so only apply to fields you never search.

### Phase 6: Security regression tests and dependency audit (S16)

Replace the default Breeze-only coverage with a table-driven authorization suite:
- Build a matrix of **role x route x HTTP verb**, taken from `Route::getRoutes()` for the `admin.*` names, asserting: Super Admin -> allowed; Doctor/Receptionist/Accountant -> allowed or 403 exactly as in the permission matrix (Receptionist: patients view/create/update, visits view-only, appointments full; Accountant: reports only).
- Tests for: inactive user cannot log in; login throttle after 5 failures; forced password change redirects every other route; last-Super-Admin protections on every path; appointment form throttle and honeypot; 422 (not 500) on malformed visit payloads.
- Run `composer audit` and `npm audit`, and report (do not blindly auto-upgrade) any findings. Run `vendor/bin/pint --test` and `php artisan test`.

### Phase 7: Design fixes

**D1. Admin layout (biggest visible problem).** `AuthenticatedLayout.jsx` puts 15 links in one top bar, which overflows below roughly 1280px. Replace it with a **left sidebar** (collapsible on mobile, bottom sheet or drawer under 768px) grouped as:
- *Clinical:* Dashboard, Patients, Visits, Appointments
- *Knowledge base:* Medicines, Symptoms, Mappings, Advice, Restrictions
- *Administration:* Doctors, Settings, Reports, Users, Roles, Logs (each group renders only if the user has at least one permission in it, and each link is still permission-filtered)

**D2. One design system.** The public site uses hardcoded teal hex values (e.g. `#147a96`, `#d8f1ff`) while the admin uses stock Breeze blue/gray. Define a `primary` palette in `tailwind.config.js` (teal scale), `surface`/`ink` neutrals, and use tokens in both Blade and React. Remove ad-hoc `bg-blue-500`/`text-blue-600` from admin pages.

**D3. Shared components.** Today every Index page repeats an unstyled table, pagination built with `dangerouslySetInnerHTML`, and a browser `confirm()` delete. Build `<PageHeader>`, `<DataTable>` (wrapped in `overflow-x-auto`, with empty and loading states), `<Pagination>` (rendered from `links` without raw HTML), `<ConfirmDialog>` (accessible modal replacing `confirm()`), `<FormField>` and `<StatusBadge>`, and migrate all index/form pages to them.

**D4. Public site responsiveness.** `layouts/public.blade.php` has a single non-wrapping row of 5 links, so it breaks on phones. Add an accessible hamburger menu (button with `aria-expanded`, keyboard operable), a sticky header, active-link styling, and a visible "Book an Appointment" button.

**D5. Bilingual public site.** The content has `_bn` fields and the doctor is Bangla-speaking, but the public site is English-only and `<html lang="en">` is fixed. Add an EN/BN toggle (stored in a cookie), set `<html lang>` dynamically, and **self-host Noto Sans Bengali** (woff2, `font-display: swap`) because Figtree has no Bangla glyphs and the Bunny Fonts CDN is an external dependency. Self-host Figtree too.

**D6. Content and trust.** `about.blade.php` is still two generic paragraphs that include an unverified claim ("over a decade"). Make About content editable in Settings (`about_text`, `about_text_bn`), show the real doctor profile, registration number, chamber address and visiting hours, and remove any claim the doctor has not supplied. Avoid cure/guarantee language on a medical site.

**D7. Branding.** `APP_NAME` is still `Laravel`, so admin page titles say "Laravel"; `ApplicationLogo.jsx` is still the Laravel logo; `public/favicon.ico` is a 0-byte file. Set the app name, render the clinic logo from Settings (fallback to a simple monogram), and add a real favicon and `<meta name="description">`/Open Graph tags on public pages.

**D8. Accessibility.** The hero text `#147a96` on `#d8f1ff` has a contrast ratio of about 4.2:1, which fails WCAG AA for normal-size text (white on `#147a96` passes at about 4.9:1). Darken the text color, add visible focus rings, `alt` text on every image, labels tied to inputs, `aria-label`s and keyboard support on the doctor carousel, and respect `prefers-reduced-motion`.

**D9. Performance.** Remove the hotlinked Unsplash background in `home.blade.php` (a decorative image at 4% opacity that costs an external request and leaks visitor IPs). Convert uploaded photos to WebP with `width`/`height` attributes and `loading="lazy"`.

**D10. Prescription PDF (functional bug, not just looks).** `resources/views/pdf/prescription.blade.php` uses `display: flex`, which **dompdf does not support**, so the patient header and the two-column layout will collapse. It also has a typo (`w-full: 100%`). Rebuild the layout with tables or floats to mirror the paper pad: letterhead, patient number/name/age/date row, left "C/C & symptoms" column, right "Rx" table with Bangla timing labels (সকাল/দুপুর/বিকাল/রাত্রি), then the advice and restrictions footers. Test with real Bangla text and confirm the Noto Sans Bengali font renders.

**D11. Doctor linkage (logic gap exposed by the design).** The prescription header still prints the single doctor from `clinic_settings`, but the app now has a `doctors` table. Add a nullable `doctor_id` foreign key on `visits`, a "Treating doctor" select on the visit form (defaulting to the logged-in doctor's linked profile), and print that doctor's name, credentials and registration number on the PDF.

**D12. Visit form UX.** After the patient combobox from Phase 3, make the prescription rows mirror the paper form (up to 5 rows, timing checkboxes, before/after toggle, dose, dilution), show symptom-based suggestions with their match score, autosave drafts, and add a print preview.
